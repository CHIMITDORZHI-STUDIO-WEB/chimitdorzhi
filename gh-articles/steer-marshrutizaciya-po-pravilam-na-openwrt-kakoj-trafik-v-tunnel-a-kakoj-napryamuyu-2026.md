# steer на OpenWrt: что идёт в туннель филиала, что напрямую

>
  **Коротко.** steer (репозиторий splify2/steer, лицензия GPL-3.0) это ядро маршрутизации по правилам для роутеров с OpenWrt. Правила пишутся в одном файле YAML или JSON, и программа одной транзакцией превращает их в правила nftables, таблицы маршрутов и наборы адресов. Для филиала это способ сказать роутеру: 1С, камеры и сеть головного офиса идут в корпоративный туннель, остальное напрямую. Проект очень молодой: репозиторий создан 2 августа 2026 года, почти все коммиты сделал один человек. Я прочитал документацию на 17.11.2026, на роутере не запускал.

## Филиал, где половина трафика должна идти в туннель

Типичная картина: в филиале роутер на OpenWrt, к головному офису поднят туннель, а в него по ошибке уходит всё. Видео на ноутбуках бухгалтерии съедает канал, и 1С тормозит. Или наоборот: туннель настроен на одну подсеть, и камеры до сервера записи не доходят. Руками это чинится парой команд, но через полгода никто не помнит, какая команда зачем.

Как соединить офисы без центрального сервера, я разбирал в [статье про EasyTier](/blog/easytier-mesh-set-mezhdu-filialami-bez-centralnogo-servera-1s-kamery-printery-2026/). Здесь следующий вопрос: когда туннель есть, как описать, что именно через него ходит.

## Что за проект и что я проверил

Проверял 17.11.2026 по README, документации и данным GitHub. Файл LICENSE содержит GPL-3.0, README называет сторонние компоненты: libyaml (MIT), wolfSSL (GPL-3.0), ngtcp2 (MIT). Платных модулей там нет.

Возраст и активность: создан 2 августа 2026 года, последний релиз 2.1.4 вышел 13 ноября, накануне 2.1.3. У автора с ником xyzmean больше тысячи коммитов, у остальных единицы. Звёзд около 150, форков 6. Для ядра, которое стоит между офисом и интернетом, это очень мало истории: один основной автор, три с половиной месяца, релизы почти ежедневно.

Есть и нюанс. Судя по плагинам (VLESS, hysteria2) и примеру со списком блокировок в README, проект вырос из личных прокси-туннелей. Этот разбор о другом: корпоративный туннель между офисами. Про обход блокировок я не пишу.

## Как задаются правила и какие туннели поддерживаются

Файл лежит в /etc/steer/spec.yaml. По спецификации обязателен только version: 2, неизвестные ключи считаются ошибкой, ошибки указывают файл, строку и столбец. Ниже мой пример по схеме из docs/spec-v2.md, не запускавшийся на роутере.

version: 2
lan: { devices: [br-lan] }
lists:
  office: { prefixes_file: lists/office.lst }
outputs:
  hq: { kind: interface, device: wg0, on_fail: drop }
rules:
  - { name: rabota, to: [office], out: hq }

В lists/office.lst подсети по одной в строке: например 10.10.0.0/24 (сервер 1С) и 10.10.5.0/24 (регистратор камер). Выход hq это обычный интерфейс wg0, то есть уже настроенный туннель. Правила проверяются сверху вниз, побеждает первое совпавшее, остальное идёт напрямую.

В ядре есть выход interface: любой существующий интерфейс, например WireGuard или OpenVPN средствами самой OpenWrt, плюс AmneziaWG. Остальное ставится плагинами из пакета ядра, сеть для установки не нужна: VLESS/Reality, hysteria2, trojan, shadowsocks, socks, http, vmess, xsteer, Cloudflare WARP, WireGuard поверх «фейкового TCP». Для филиалов главный вариант это interface, плагины я не рассматривал.

## Что значит «атомарная транзакция» и что нужно роутеру

По документации ядро применяет набор правил nftables одной командой nft -f, таблица пересоздаётся без момента, когда её нет. Если nft набор отвергнет, он сохраняется в файле steer-ruleset.rejected. Режим steer apply --dry-run печатает итог и ничего не меняет.

Подтверждено не всё. В architecture.md старые метки удаляются только после удачной загрузки, но фразы «при ошибке прежние правила остаются» там нет. Для маршрутов (ip rule, ip route) атомарность и откат не описаны, обновление fake-IP идёт отдельными транзакциями. Откат при ошибке как гарантию я не обещаю: проверять на тестовом роутере. Порядок такой: dry-run, apply, прежний файл правил под рукой.

По docs/guide.md: OpenWrt 22.03 и новее, ядро Linux 5.2 и выше, пакеты nftables, ip-full, conntrack, kmod-nft-queue, kmod-tun. Сборки для 11 архитектур (aarch64, arm, mipsel, mips, x86_64). Полный набор протоколов весит около 3,8 МБ на mipsel. Минимум памяти в документации не указан, поэтому на самый слабый роутер без запаса я бы не ставил.

## Как проверить, что правила применились и нет утечки

Свои инструменты: steer status (состояние и счётчики), steer diag (проверки, код 1 при сбое), steer explain 10.10.0.5 (какое правило ловит адрес и какой выход использует), steer conns (выход каждого соединения). Отдельной процедуры проверки утечек в документации нет.

Мой порядок штатными средствами OpenWrt, здесь не запускавшийся: ip route get 10.10.0.5 на роутере; трассировка с компьютера филиала до сервера 1С; затем отключить туннель и убедиться, что обращения к 1С не уходят в интернет (при on_fail: drop трафик останавливается). Если 1С открывается по имени, проверить, какой DNS отвечает. По документации, в режиме fake-IP трассировка показывает служебный адрес из 198.18.0.0/15.

## Чем отличается от старых способов и что важно учесть

Ручной policy-based routing (ip rule, свои таблицы) работает без пакетов, но держится на памяти администратора. mwan3 решает другую задачу: несколько каналов, переключение и баланс (по общим знаниям, страницу OpenWrt я открыть не смог). pbr, судя по странице проекта, задаёт политики по адресу, MAC, порту, протоколу и домену, поддерживает WireGuard и OpenVPN, есть интерфейс LuCI. История у pbr намного длиннее.

steer интереснее, когда нужны правила по именам через fake-IP, группы выходов, привязка по MAC и один файл для Git. Если в туннель идут две-три известные подсети, лучше статический маршрут или pbr: молодой пакет на границе сети не нужен.

Проект быстро меняется, любой релиз сначала на тестовый роутер. Открытые обращения в репозитории в основном про прокси-функции, к офисному сценарию не относятся. Поддержка это канал в Telegram и сам автор, гарантий нет. На слабом роутере с нестандартной прошивкой я бы остался на статических маршрутах. Юридическую сторону корпоративных туннелей я не проверял.

## Что можно сделать уже сейчас

- Выписать, что идёт в туннель: подсети 1С, камер, принтеров. Остальное остаётся напрямую.

- Проверить версию и архитектуру: cat /etc/openwrt_release. Старше 22.03 не подойдёт.

- Поднять тестовый роутер, поставить steer-core и пройти dry-run, apply, explain, diag. Затем отключить туннель и посмотреть на трафик.

- Подключить мониторинг: [Uptime Kuma](/blog/uptime-kuma-monitoring-dostupnosti-2026/) покажет, когда туннель или 1С недоступны.

Настройку филиалов и удалённого доступа на вашем оборудовании (туннель, правила маршрутов, проверка, откат) я делаю в рамках услуги [защищённого удалённого доступа](/services/secure-remote-access/). Для небольшого офиса есть [разовая IT-настройка](/blog/it-nastroyka-malenkogo-ofisa-razovo-2026/), цены на [странице цен](/ceny/).

## Частые вопросы

### Нужен ли steer при одном туннеле и двух подсетях?

Скорее всего нет: статический маршрут или pbr проще. steer оправдан, когда правил много, нужны домены, группы выходов или привязка к устройствам.

### Можно ли описать правила в JSON?

По спецификации да, файл, начинающийся с «{», читается как JSON. Пример в README только в YAML, JSON я не проверял.

### Что будет, если туннель упадёт?

При on_fail: drop (по умолчанию) трафик правила останавливается, а не идёт в обход. Значение direct отправит его напрямую.

## Коротко о главном

steer удобен как единый читаемый файл правил поверх работающего туннеля, но проект молодой, с одним основным автором, и откат при ошибке в документации описан не полностью. Для филиалов я бы брал его после проверки на тестовом роутере, а на простых схемах оставил статические маршруты или pbr.
