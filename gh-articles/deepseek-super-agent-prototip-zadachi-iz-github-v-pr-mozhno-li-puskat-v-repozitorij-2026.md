# DeepSeek Super Agent: можно ли пускать его в репозиторий

>
  **Коротко.** dsh-superagent от DeepSeek (MIT, создан 31.10.2026) это исследовательский прототип: агент слушает GitHub, по просьбе человека из списка берёт задачу, готовит ветку и pull request. Код настоящий, но авторы сами пишут, что это не продукт и не для боевой среды. Песочницы нет: агент работает с правами пользователя операционной системы. Звёзды (23 736 на 18.11.2026) о безопасности не говорят. К рабочему репозиторию клиента я бы его не подключал. Пробовать можно на отдельной машине и на тестовом репозитории.

## Заказчик спрашивает: пусть агент сам берёт задачи

Всё чаще слышу такое: «Вот у DeepSeek вышел агент, который сам берёт задачи из GitHub и делает pull request. Давайте подключим к нашему репозиторию». Звучит заманчиво, поэтому я 18.11.2026 прочитал репозиторий [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype): README, девять документов, подсказки агентов и код. Установку и запуск я не делал: ниже то, что видно из текста и API GitHub.

## Что это на деле

Отдельной программой он не работает: это пакет-расширение для DeepSeek Harness (DSH), другого проекта DeepSeek. По карточке на GitHub DSH находится в developer preview, и авторы предупреждают о несовместимых изменениях. Нужны Node.js 22.19+, pnpm, tmux, Python, GitHub CLI и конкретная версия DSH. Лицензия MIT, файл LICENSE на месте, отдельных платных модулей я не нашёл. В репозитории настоящий код на TypeScript, около шестидесяти файлов с тестами (я их не запускал), документы и подсказки. В main одна запись истории от 31.10.2026 и один автор, «DeepSeek Harness Team». По API последняя загрузка была 03.11.2026. Обращения на GitHub выключены, поэтому «0 открытых обращений» ничего не доказывает.

README прямо говорит: исследовательский прототип, не официальный продукт, не готов к боевой работе, часть идей из статьи авторов не реализована.

## Права и изоляция

Агенту нужен отдельный пользовательский аккаунт GitHub с правом записи в репозиторий: GitHub App не подходит, потому что агент читает уведомления аккаунта. Какие именно области токена нужны, я в документах и коде не нашёл. Проверка при настройке подтверждает доступ на чтение и push.

Агент комментирует, создаёт ветки с префиксом agent/, пушит и открывает pull request. Он запускает команды и тесты. Автослияние по умолчанию выключено, а от имени аккаунта агента включать его запрещено.

Песочницы нет. В документации сказано, что обе роли работают с режимом danger-full-access от имени пользователя ОС, команды выполняются без подтверждения, обёртки над gh и git лишь задают умолчания и границей безопасности не служат. Агент может читать домашнюю папку. Авторы советуют отдельного пользователя ОС. От вредных задач защищают список разрешённых логинов и подсказки: текст задач, комментариев и файлов считается недоверенными данными. Это защита на уровне инструкций модели, и проверок на подмену инструкций в тексте задачи я не видел. В самой статье авторов безопасность названа открытой проблемой (по пересказу на стороннем ресурсе, оригинал я не нашёл). Как ограничивают права исполнителей, я разбирал в статье про [Omnara](/blog/omnara-zapusk-ii-agentov-u-sebya-prava-dostupa-i-sekrety-2026/).

## Куда уходит код и содержимое задач

В коде пакета я не нашёл адресов серверов моделей: модель выбирается в настройках DSH. Какие провайдеры поддерживает DSH, я не выяснил. Значит, текст задач и куски кода уйдут туда, куда направлен ваш DSH: к DeepSeek, к другому облаку или на свою модель. Для коммерческой тайны это вопрос договора и настроек, отдельного закона я не проверял.

Если в репозитории или задачах есть персональные данные граждан России, действуют нормы 152-ФЗ. По тексту на consultant.ru: [часть 3 статьи 12](https://www.consultant.ru/document/cons_doc_LAW_61801/e4ebbe1780de623c7cf32a59ca82a7bb523a25dd/) обязывает оператора до начала трансграничной передачи уведомить уполномоченный орган, а [часть 5 статьи 18](https://www.consultant.ru/document/cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/) не допускает при сборе данных граждан РФ запись, хранение и обновление в базах за пределами России, кроме случаев из пунктов 2, 3, 4 и 8 части 1 статьи 6. Попадает ли ваш случай под эти нормы, решает юрист.

## Звёзды и цифры: что я измерил

По API на 18.11.2026 у репозитория 23 736 звёзд, 2 931 форк и 180 подписчиков. Репозиторию 18 дней, значит в среднем около 1 300 звёзд в день. Список звёздочников GitHub отдаёт только с авторизацией, токена у меня не было, поэтому кривую за всё время и выборку по всей истории я построить не смог.

Что смог, из публичной ленты событий. В ней последние 300 событий: с 17.11 00:32 до 18.11 07:37 по UTC, 253 звезды и 47 форков. На 17.11 пришлось 184 звезды, не больше 16 в час, то есть заметно меньше среднего. Из этих 253 я случайно взял 16 аккаунтов: три созданы в 2026 году, три в 2024 и 2025 годах, десять раньше, у трёх нет публичных репозиториев. По номеру аккаунта (он растёт со временем) 35 из 253, то есть 13,8%, созданы не раньше конца февраля 2026. У соседнего репозитория той же организации, deepseek-harness, в 70 последних звёздах таких 16, то есть 22,9%. В моём окне избытка новых аккаунтов нет, но первые дни, когда пришла основная масса, я не видел. Как проверять звёзды самому: [starsift](/blog/starsift-kak-proverit-chto-u-open-source-proekta-nastoyaschie-zvezdy-pered-vnedreniem-2026/) и [общая проверка популярности](/blog/kak-proverit-populyarnost-open-source-pered-vnedreniem-nakrutka-zvezd-github-i-starsift-2026/). Выводов о причинах роста не делаю.

Бенчмарков качества кода у проекта нет, ни SWE-bench, ни аналогов. Цифры из статьи авторов (медиана и 95-й процентиль времени 12,4 и 15,7 минуты против 20,4 и 29,5 у одной сессии) по пересказу на стороннем ресурсе сняты на синтетической нагрузке, где работа программиста заменена таймером, по пять запусков. Такое измерение показывает скорость планирования и ничего не говорит о качестве правок. Сами авторы называют его ориентировочным.

## Что важно учесть

Прототип рассчитан на команду, где за агентом смотрят каждый день: панель, список разрешённых, настройка подсказок. Настройка по SETUP.md предполагает, что её проведёт другой агент. Версии DSH и пакета меняются, история в репозитории пока из одного коммита. В текстах по умолчанию есть шаг с переписыванием истории и push --force-with-lease в ветку самого агента, поэтому защита основных веток обязательна.

## Что можно сделать уже сейчас

Если заказчик хочет автономного агента, вот схема, которую я собираю в рамках [разработки ИИ-агентов](/services/ai-agents/):

- Отдельный аккаунт агента с записью в один репозиторий, без прав администратора. В основных ветках запрет прямых пушей и force-push, обязательный pull request и одобрение человека.

- Отдельная машина или пользователь ОС без чужих секретов и ключей, а в репозитории нет файлов .env. Наружу доступны только GitHub и выбранная модель.

- Список из одного-двух логинов, кто может ставить задачи, режим observe, лимит одновременных задач и расходов у провайдера модели, журнал действий и разбор раз в неделю.

- Обязательное ревью и автопроверка перед слиянием, как в статье про [no-mistakes](/blog/no-mistakes-avtoproverka-koda-pered-otpravkoy-chto-trebovat-ot-studii-2026/). Автослияние выключено.

## Частые вопросы

### Можно ли подключить его к боевому репозиторию?

Авторы не рекомендуют, и я согласен. Сначала тестовый репозиторий без секретов, на отдельной машине.

### Нужен ли API DeepSeek?

В пакете адресов моделей нет, модель задаётся в DSH. Какие провайдеры поддерживает DSH, я не проверял.

### Если звёзд много, значит безопасно?

Нет, число звёзд не говорит ни о правах, ни об изоляции. Эти вопросы закрывает чтение кода и настройка окружения.

## Коротко о главном

dsh-superagent показывает, как может работать агент, берущий задачи из GitHub, но это прототип без песочницы и без бенчмарков качества, зависящий от DSH. Звёзды и MIT делают его заметным, а безопасным делают отдельный аккаунт, минимальные права, защищённые ветки, ревью, лимиты и журнал.
