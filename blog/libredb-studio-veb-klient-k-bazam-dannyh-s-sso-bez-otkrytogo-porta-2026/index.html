LibreDB Studio: веб-клиент к базам с SSO и без открытого порта

LibreDB Studio это веб-редактор баз данных, который ставится рядом с данными через Docker или npx. Разбираю по репозиторию и документации: вход через OIDC, две роли, где лежат пароли, что уходит ИИ-модели и почему «только чтение» надо делать на самой базе.

LibreDB Studioбазы данныхSSOopen source
Коротко. LibreDB Studio (репозиторий libredb/libredb-studio, лицензия MIT) это веб-редактор баз данных, который ставится рядом с данными: Docker-образ или npx. Один интерфейс для PostgreSQL, MySQL, MongoDB, Redis, ClickHouse, SQLite и других (заявлено 41 движок), ER-диаграммы, сравнение схем, вход через OIDC и выключенный по умолчанию ИИ-помощник. Ролей всего две, и обычный пользователь по документации может выполнить любой запрос, поэтому «только чтение» для аналитиков настраивают на самой базе. Проекту десять месяцев, версия 1.0.0 вышла 17.10.2026, сам я его не запускал.

Свой веб-клиент к базам: SSO, роли, только чтение

Порт базы наружу или пароль в чат

Аналитик просит посмотреть заказы. Программист даёт пароль от базы или открывает порт в интернет, потому что так быстрее. Через месяц пароль лежит в трёх чатах, порт открыт, а что и когда запускали, не знает никто.

Для базы бота в одном файле у меня есть разбор про DB Browser for SQLite. Если нужны таблицы вместо SQL, подойдут NocoDB и Baserow. LibreDB Studio решает третью задачу: живая база на сервере, к ней ходят несколько человек, и у каждого свой вход. Порт базы остаётся внутри сети, наружу смотрит одна страница Studio за входом.

Что это за проект и что я проверил

Проверял 19.10.2026 по репозиторию и документации. Репозиторий создан 23 декабря 2025 года, не архивирован, около 1,2 тысячи звёзд и 265 форков. Последний коммит от 19 октября, релиз 1.0.0 вышел 17 октября. Файл LICENSE содержит MIT, правообладатель турецкая компания SEKOYA GRUP BİLİŞİM VE TEKNOLOJİ LİMİTED ŞİRKETİ, в SECURITY.md она названа поддерживающей стороной. Участников больше сотни, но около 1300 коммитов из 2138 сделал один человек.

Ставится одной командой: docker run -p 3000:3000 ghcr.io/libredb/libredb-studio:latest или npx @libredb/studio (нужен Node.js 24 или новее). Есть Helm-чарт, пакеты deb и rpm. Пароль администратора печатается в журнал при первом запуске.

По README, 41 движок со своими драйверами (PostgreSQL, MySQL, SQL Server, Oracle, SQLite, MongoDB, Redis, ClickHouse, Elasticsearch, Snowflake, Kafka и другие) и ещё 27 совместимых по протоколу, например MariaDB. 1С в списке нет. Ещё заявлены ER-диаграммы с экспортом в PNG и SVG, сравнение двух снимков схемы и готовый SQL миграции для PostgreSQL, MySQL, SQLite, Oracle и SQL Server.

Вход, роли и режим «только чтение»

Вход бывает локальный или через OIDC, переключается переменной NEXT_PUBLIC_AUTH_PROVIDER=oidc. По docs/OIDC.md это работает с Keycloak, Okta, Azure AD, Zitadel и Google, с PKCE. Роль берётся из поля токена (OIDC_ROLE_CLAIM): значения из OIDC_ADMIN_ROLES дают администратора, остальные становятся пользователем. Если единый вход у вас уже поднят, как в статье про Keycloak, Studio подключается к нему как ещё один сервис.

Ролей две, admin и user. Раздел Known limits в docs/SECURITY.md говорит прямо: user может подключиться к любому хосту и порту и выполнить любой запрос, политик по таблицам и схемам нет, их авторы называют нереализованным направлением. Есть ALLOW_CUSTOM_CONNECTIONS=false: пользователи не создают свои подключения, остаются только заданные администратором, а пароль такого подключения (managed) лежит на сервере.

Флаг readOnly: true у заданного подключения существует, но работает на части движков: etcd, Neo4j, Milvus, Qdrant, InfluxDB, S3 и Kubernetes. На остальных конфиг с этим флагом просто не загрузится. Для PostgreSQL и MySQL «только чтение» делайте там, где оно надёжно: отдельная учётная запись в базе с правом SELECT на нужные таблицы или представления. Тот же принцип я разбирал в статье про MCP Toolbox.

Где лежат пароли и что пишется в журнал

В локальном режиме Studio держит подключения в localStorage браузера открытым текстом, документация называет это известным ограничением. В серверном режиме (STORAGE_PROVIDER=sqlite или postgres) пароли, строки подключения и SSH-ключи шифруются AES-256-GCM, а адрес, порт и имя пользователя остаются читаемыми. Ключ по умолчанию выводится из JWT_SECRET, при SQLite он лежит в одной папке с базой, и копия тома уносит ключ вместе с шифртекстом. Задайте STORAGE_ENCRYPTION_KEY снаружи тома.

Вкладка Audit у администратора показывает историю запросов и выгружает её в CSV или JSON. События входа и отказы по правам идут строками JSON в stdout. README сам оговаривает, что запросы, набранные вручную в редакторе, не проходят ту же проверку политик и аудита, что запуски ИИ-агента. Что попадёт в журнал в вашей схеме, проверьте на тесте.

ИИ-режим: что уходит наружу

Пока не заданы LLM_PROVIDER, LLM_API_KEY и LLM_MODEL, панели ИИ в интерфейсе нет и ничего не отправляется. Модель на выбор: Gemini (по умолчанию), OpenAI, локальный Ollama или любой OpenAI-совместимый адрес вроде LM Studio и vLLM. Ollama и свой адрес считаются настроенной моделью и без ключа.

По docs/AGENT_DATA_FLOW.md модели уходят ваш вопрос и перечень таблиц, столбцов и индексов с типами. В режиме агента добавляются строки результатов, до 200 на одно чтение. Сводка профилировщика отправляет минимумы и максимумы столбцов, а это реальные значения. Пароли подключений в запрос не попадают. Про персональные данные и зарубежную модель смотрите норму в статье про MCP Toolbox и спросите юриста. С локальной моделью данные остаются у вас.

Агент читает данные только на PostgreSQL, SQLite, DuckDB, SQL Server, MySQL, MongoDB и Kubernetes, на остальных движках запуск с запросами отклоняется. Предложенное агентом выполняет человек. Перед DELETE, DROP и TRUNCATE Studio просит подтверждение, с настроенной моделью добавляется оценка риска. Про UPDATE без WHERE в README ничего не нашёл.

Что важно учесть

Сам инструмент становится мишенью: в нём лежат доступы ко всем подключённым базам. Держите Studio за VPN или за HTTPS с SSO и обновляйте: SECURITY.md обещает исправления только для последнего релиза.

Проект молодой: версия 1.0.0 появилась два дня назад, развитие держится на одной компании и одном главном разработчике. Маскирование значений в интерфейсе работает только в браузере и сервером не обеспечивается. README есть и на русском, а русский интерфейс я не нашёл. Доступность из России (Docker-реестры, внешние модели) уточняйте.

Что можно сделать уже сейчас

Заведите в каждой базе отдельного пользователя только на чтение с доступом к нужным таблицам.

Поставьте Studio на тестовую копию базы с локальными учётными записями, подключите её заданным подключением и проверьте три вещи: что создать своё подключение пользователь не может, что запись с учётки только на чтение отклоняется, что запросы видны во вкладке Audit.

Если единого входа нет, сначала решите, чем он будет. Развернуть Studio, SSO и роли можно в рамках услуги по кибербезопасности.

Частые вопросы

Нужно ли открывать порт базы?

Нет, Studio подключается к базе из своей сети, как любое приложение. Открытой остаётся только его веб-страница, если люди заходят снаружи, и лучше закрыть её VPN.

Можно ли без ИИ?

Да, это поведение по умолчанию. Без переменных LLM_* панель ИИ не показывается.

Заменит ли Studio BI-систему?

Графики в нём есть, но дашборды для руководителя удобнее собирать в BI-системе. Studio нужен тем, кто работает с таблицами и запросами.

Коротко о главном

LibreDB Studio под MIT даёт команде один веб-вход ко многим базам с OIDC, журналом и ИИ-помощником по желанию. Права на чтение и запись при этом определяет сама база, а не Studio, поэтому первым делом нужен пользователь только на чтение.
